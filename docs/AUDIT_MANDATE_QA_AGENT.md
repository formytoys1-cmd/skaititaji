# Мандат агента-аудитора качества (QA / Security Audit Agent)
## Проект: Skaitītāji — платформа подачи показаний счётчиков воды

> **Назначение документа.** Это техническое задание и мандат для автономного
> **агента-тестера/аудитора**, которого проект запускает у себя как «стороннего
> аудитора». Документ содержит: (1) роль и правила работы агента, (2) реестр
> находок с доказательствами и критериями приёмки, (3) стратегию тестирования и
> перечень тест-наборов к реализации, (4) интеграцию с CI, (5) маршрутизацию по
> моделям ИИ. Агент должен **реализовать** описанное, а не только советовать.
>
> **Составлено:** сторонним аудитором (сессия-ревью), 2026-08-20.
> **Кодовая база на момент аудита:** FastAPI + SQLModel (~5 600 строк Python,
> 50 коммитов), Jinja2/PWA-фронтенд, каркас Expo/RN, интеграция Visma Horizon
> (mock), деплой Docker/Render. **Тестов в репозитории — 0.**

## Часть 0. Что уже сделано хорошо (не ломать)

Аудит подтверждает зрелую базовую гигиену — эти механизмы **сохранить и покрыть
тестами**, а не переписывать:

- Заголовки безопасности + **HSTS** на HTTPS, `COOP`, `X-Permitted-Cross-Domain`
  ([app/main.py](../app/main.py)).
- Сессионная cookie **HttpOnly**, `SameSite=Lax`, **Secure в проде**
  (`https_only=_is_prod`), `max_age=8ч`.
- Пароли — **PBKDF2-SHA256, 120 000 итераций**, сравнение через
  `hmac.compare_digest` ([app/auth.py](../app/auth.py)).
- **Agent API** отключается, если ключ не задан (503), а не открывается по умолчанию
  ([app/routers/agent_api.py](../app/routers/agent_api.py)).
- Ролевой доступ через `require_role(...)`, мультиарендная модель на `Organization`.

## Часть 1. Роль и правила работы агента-аудитора

### 1.1 Персона и цель
Ты — **независимый агент контроля качества и безопасности**. Твоя цель — довести
проект от «рабочего MVP» до **production-ready** через:
1. воспроизведение и подтверждение каждой находки из реестра (Часть 2);
2. написание **автоматических тестов**, доказывающих проблему (red) и её
   устранение (green);
3. реализацию исправлений строго по критериям приёмки;
4. настройку CI, чтобы регрессии не возвращались.

### 1.2 Границы (обязательно соблюдать)
- **Не трогать mock-режим Visma как дефолт демо** — реальные вызовы только за
  флагом/в отдельном e2e-профиле.
- **Не коммитить секреты.** Любые ключи/пароли — только через окружение.
- **Не ослаблять** уже существующие механизмы безопасности из Части 0.
- **Персональные данные** (жители, лицевые счета) в тестах — только синтетические.
- Не переименовывать публичные маршруты и коды REST-сервисов Horizon.

### 1.3 Режим работы (для каждой находки)
1. **Reproduce** — тест, падающий на текущем коде (red), со ссылкой на файл/строку.
2. **Fix** — минимальное корректное изменение.
3. **Verify** — тот же тест зелёный + не сломаны соседние.
4. **Guard** — тест остаётся в CI как страховка от регрессии.
5. **Document** — короткая запись в CHANGELOG/находке: было → стало.

### 1.4 Definition of Done (общий)
- Все находки **Critical/High** закрыты, есть покрывающие тесты.
- `pytest` зелёный в CI; покрытие ключевых модулей (`auth`, `services`,
  `integrations`, роутеры) — **≥ 80 %**.
- Прод-конфиг проходит проверку «boot-guard» (Часть 2, SEC-004).
- README/docs обновлены; добавлен `docs/SECURITY.md` и `docs/TESTING.md`.

### SEC-001 · 🔴 Critical · Незащищённый вход `demo-login` в проде

- **Где:** [app/routers/auth.py](../app/routers/auth.py) — `GET /demo-login?role=...`.
- **Доказательство:** эндпоинт не проверяет `settings.debug`/окружение и логинит
  одним кликом под `resident@demo.lv`, `manager@demo.lv`, `admin@demo.lv`. Если
  сид демо-данных попадёт в прод-БД, любой посетитель получит **роль admin**.
- **Влияние:** полный обход аутентификации, повышение привилегий до администратора,
  доступ к данным всех арендаторов.
- **Воспроизвести:** на инстансе с демо-сидом открыть `GET /demo-login?role=admin`
  → сессия администратора без пароля.
- **Что сделать:** гейт `if settings.debug and not _is_prod` — иначе `404`.
  Демо-аккаунты **не сидировать** в прод (флаг `SEED_DEMO`). Отдельный явный
  `ALLOW_DEMO_LOGIN=0` по умолчанию.
- **Приёмка:** в прод-профиле `GET /demo-login` → 404; в dev — работает.
- **Тест:** `test_demo_login_disabled_in_prod`, `test_demo_login_enabled_in_dev`.

### SEC-002 · 🔴 Critical · Дефолтный `SECRET_KEY` и `DEBUG=1`

- **Где:** [app/config.py](../app/config.py) — `SECRET_KEY="dev-secret-change-me"`,
  `DEBUG` по умолчанию `1`.
- **Доказательство:** подписанные сессии используют предсказуемый ключ; при
  случайном деплое без переменных окружения куки можно **подделать**.
- **Влияние:** подделка сессии → вход под любой ролью; включённый DEBUG раскрывает
  трейсбеки и внутренние детали.
- **Что сделать:** «boot-guard» (см. SEC-004): в проде падать при дефолтном ключе;
  `DEBUG` по умолчанию `0`; сгенерировать ключ при dev-старте, если не задан.
- **Приёмка:** прод-старт с дефолтным `SECRET_KEY` завершается ошибкой конфигурации.
- **Тест:** `test_boot_fails_on_default_secret_in_prod`.

### SEC-003 · 🟠 High · Секреты интеграции Visma хранятся в открытом виде

- **Где:** `Organization.integration_config` (JSON в БД),
  [app/integrations/registry.py](../app/integrations/registry.py) читает
  `cfg["password"]`.
- **Доказательство:** пароль пользователя Horizon кладётся в JSON-поле БД без
  шифрования; попадает в дампы, логи, бэкапы.
- **Влияние:** утечка учётки к бухгалтерской системе арендатора (NĪP/KNS).
- **Что сделать:** шифровать секреты at-rest (Fernet/KMS-обёртка), либо хранить в
  секрет-хранилище и держать в конфиге только ссылку; маскировать в логах/админке.
- **Приёмка:** пароль не читается из БД в открытом виде; в UI показывается `••••`.
- **Тест:** `test_integration_secret_encrypted_at_rest`,
  `test_secret_masked_in_admin_view`.

### SEC-004 · 🟠 High · Нет «boot-guard» валидации прод-конфигурации

- **Где:** старт приложения ([app/main.py](../app/main.py), `app/config.py`).
- **Доказательство:** приложение стартует с любыми (в т.ч. небезопасными)
  значениями; признак прода определяется эвристикой по env-переменным.
- **Что сделать:** функция `validate_production_config()` при `_is_prod`:
  запрет дефолтного `SECRET_KEY`, `DEBUG=0`, `DATABASE_URL` не sqlite,
  `ALLOW_DEMO_LOGIN=0`, заданы CORS/hosts. Падать с понятным сообщением.
- **Приёмка:** запуск с невалидным прод-конфигом → немедленная ошибка со списком
  проблем.
- **Тест:** `test_production_config_validation` (таблица валидных/невалидных наборов).

### SEC-005 · 🟠 High · Нет CSRF-защиты POST-форм

- **Где:** формы во всех роутерах (`auth`, `resident`, `manager`, `management`,
  `moderator`).
- **Доказательство:** защита опирается только на `SameSite=Lax`; для POST этого
  недостаточно (GET-навигация, вложенные контексты, старые браузеры).
- **Что сделать:** CSRF-токен (double-submit cookie или подпись в сессии),
  скрытое поле в формах Jinja, проверка в зависимости на всех small-mutating POST.
- **Приёмка:** POST без валидного токена → 403; с токеном → 200.
- **Тест:** `test_post_without_csrf_rejected`, `test_post_with_csrf_ok`.

---

### SEC-006 · 🟠 High · Нет rate-limiting / защиты от перебора на логине

- **Где:** `POST /login`, `POST /registreties`, `GET /demo-login`.
- **Доказательство:** нет счётчика попыток/задержек → возможен brute-force паролей
  и enumeration аккаунтов.
- **Что сделать:** лимитер по IP+email (напр. SlowAPI или собственный на БД/памяти),
  экспоненциальная задержка, единый ответ на «неверный логин/пароль» (без
  раскрытия, существует ли email).
- **Приёмка:** >N попыток за окно → 429; сообщение об ошибке не раскрывает
  существование аккаунта.
- **Тест:** `test_login_rate_limited`, `test_login_no_user_enumeration`.

### SEC-007 · 🟡 Medium · Сравнение ключа агента не константное по времени

- **Где:** [app/routers/agent_api.py](../app/routers/agent_api.py) —
  `if x_agent_key != settings.agent_api_key`.
- **Доказательство:** прямое `!=` уязвимо к timing-атаке (в отличие от паролей,
  где уже используется `compare_digest`).
- **Что сделать:** `hmac.compare_digest(x_agent_key, settings.agent_api_key)`.
- **Приёмка:** сравнение через `compare_digest`.
- **Тест:** `test_agent_key_uses_constant_time_compare` (проверка поведения +
  статическая проверка отсутствия `!=` в сравнении секретов).

### SEC-008 · 🟠 High · Изоляция арендаторов (multi-tenant) не доказана тестами

- **Где:** роутеры `manager`, `management`, `resident`, `admin`, `moderator`
  (фильтры `organization_id` присутствуют неравномерно: manager=8, management=6,
  resident=2, admin=1, moderator=0).
- **Доказательство:** мультиарендность — ядро продукта, но нет ни одного теста,
  что пользователь арендатора A **не может** читать/менять данные арендатора B
  (классический IDOR по `id` в URL).
- **Что сделать:** сквозной аудит каждого доступа к сущностям по `id`: обязательная
  проверка принадлежности к `current_user.organization_id`. Ввести helper
  `get_owned_or_404(model, id, user)`.
- **Приёмка:** попытка доступа к чужому `unit_id`/`meter_id`/`reading_id`/`thread`
  → 404/403.
- **Тест:** матрица `test_tenant_isolation_*` по всем сущностям и ролям.

### DATA-001 · 🟠 High · SQLite по умолчанию + отсутствие миграций

- **Где:** [app/config.py](../app/config.py) `DATABASE_URL=sqlite:///...`; схема
  создаётся `create_all`, миграций нет.
- **Влияние:** конкурентная запись в окно массовой подачи (конец месяца) →
  блокировки/ошибки; изменение схемы в проде без миграций → потеря данных.
- **Что сделать:** поддержать **PostgreSQL** (psycopg уже в зависимостях),
  внедрить **Alembic**, `create_all` оставить только для тестов/dev.
- **Приёмка:** миграции применяются на пустой и на непустой БД; CI гоняет тесты
  на Postgres.
- **Тест:** `test_migrations_apply_clean`, smoke на Postgres-контейнере в CI.

### DATA-002 · 🟡 Medium · Идемпотентность и параллелизм подачи показаний

- **Где:** сервис подачи ([app/services.py](../app/services.py)).
- **Доказательство:** нет явной защиты от двойной отправки/гонки при одновременной
  подаче за один период по одному счётчику.
- **Что сделать:** уникальный констрейнт (meter_id, period) или upsert; проверка,
  что новое показание ≥ предыдущего; транзакционность.
- **Приёмка:** повторная/двойная подача не создаёт дублей; регресс на убывающее
  показание отклоняется корректно.
- **Тест:** `test_reading_idempotent_same_period`, `test_reading_not_decreasing`,
  `test_concurrent_submit_no_duplicate`.

### VISMA-002 · 🟠 High · Нет ретраев/таймаутов/идемпотентности записи в Horizon

- **Где:** тот же клиент; `timeout=20` есть, но нет ретраев и защиты от двойной
  записи при обрыве.
- **Влияние:** on-premise сервер арендатора ненадёжен по сети → задвоенные акты
  показаний, рассинхрон.
- **Что сделать:** ретраи с backoff на идемпотентных операциях, ключ
  идемпотентности для записи, чёткая обработка 4xx/5xx, circuit-breaker/лог.
- **Приёмка:** сетевой сбой не приводит к дублю записи; ошибки видны в логе/статусе.
- **Тест:** `test_visma_retry_on_5xx`, `test_visma_write_idempotent_on_timeout`.

## Часть 3. Стратегия и каркас тестирования (реализовать первым)

### 3.1 Инструменты
`pytest`, `pytest-cov`, `httpx`/`TestClient` (уже есть httpx), `pytest-asyncio`,
фикстуры на in-memory/файловой SQLite для юнитов и **Postgres-контейнер** для
интеграционных, `Playwright` для e2e (уже используется в разработке).

### 3.2 Структура
```
tests/
  conftest.py            # фикстуры: app, БД на транзакции, фабрики арендаторов/юзеров
  unit/                  # auth (хэш/verify), services (валидация/аномалии), i18n
  integration/           # роутеры через TestClient: auth, resident, manager, admin
  security/              # SEC-001..008: csrf, rate-limit, demo-login, boot-guard, tenant
  contracts/             # VISMA-001/002 на замоканных httpx-ответах
  e2e/                   # Playwright: подача показания, кабинет управляющего, PWA
  factories.py           # синтетические данные (без реальных перс. данных)
```

### 3.3 Приоритет реализации (агенту — в этом порядке)
1. **QA-001** каркас + smoke (`/api/health`, старт приложения).
2. **SEC-001, SEC-002, SEC-004** (критичные, дешёвые, high-impact).
3. **SEC-008** матрица изоляции арендаторов.
4. **SEC-005, SEC-006, SEC-007**.
5. **DATA-001/002** (Postgres + Alembic + идемпотентность).
6. **VISMA-001/002** контракты и устойчивость.
7. **GDPR-001, OPS-001**.
8. **AUTH-001** (крупная веха, отдельно).

### 3.4 Целевые метрики
- Покрытие ключевых модулей ≥ 80 %.
- 0 находок Critical/High в открытом статусе.
- Время прогона юнит+интеграция < 60 c локально.

## Часть 6. Маршрутизация по моделям ИИ (какой узел — какой моделью)

Профиль проекта — **инженерия ПО**. Правило: **Sonnet — рабочая лошадка**,
**Opus 4.8 — точечно на «трудные узлы» (безопасность/внешние API/архитектура/
право)**, режим **«Высокая 1M»** — когда задача охватывает весь стек.

| Находка / задача | Модель | Почему |
|---|---|---|
| QA-001 каркас, фикстуры, типовые тесты роутеров | **Sonnet** | много типового объёма |
| SEC-001 demo-login гейт | **Sonnet** | точечная правка |
| SEC-002/004 boot-guard, конфиг прода | **Sonnet** | простая логика + тесты |
| SEC-003 шифрование секретов at-rest | **Opus 4.8** | крипто/секрет-менеджмент, цена ошибки |
| SEC-005 CSRF (дизайн) | **Opus 4.8** → реализация **Sonnet** | безопасность требует точности |
| SEC-006 rate-limit / анти-enumeration | **Opus 4.8** (дизайн) → **Sonnet** | модель угроз |
| SEC-007 constant-time compare | **Sonnet** | однострочный фикс + тест |
| SEC-008 матрица изоляции арендаторов | **Opus 4.8** | IDOR-анализ по всему коду |
| DATA-001 Postgres+Alembic (стратегия) | **Opus 4.8**; рутина миграций — **Sonnet** | стратегия vs механика |
| DATA-002 идемпотентность/гонки | **Opus 4.8** | конкурентность, транзакции |
| VISMA-001/002 контракты, ретраи, идемпотентность | **Opus 4.8** | внешний API, надёжность |
| GDPR-001 право ЛР/ЕС | **Opus 4.8** | юридический reasoning |
| OPS-001 аудит-лог | **Sonnet** | стандартный паттерн |
| AUTH-001 Smart-ID/eParaksts | **Opus 4.8** | незнакомый протокол + безопасность |
| Большой сквозной рефакторинг/отладка через весь стек | **Opus 4.8 + «Высокая 1M»** | нужен весь контекст |
| UI/шаблоны/PWA/i18n/README | **Sonnet / лёгкая** | reasoning не нужен |
