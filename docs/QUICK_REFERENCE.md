## Как работает демо (важно)
- На `/demo` и лендинге кнопки «Войти в демо» ведут на **`/login?demo=<role>`**
  (`resident`/`manager`/`admin`). Открывается форма входа с **уже заполненными**
  e‑mail и паролем — остаётся нажать зелёную кнопку «Войти».
- **Почему не «в один клик»:** в проде вход‑обход `/demo-login` **отключён**
  (SEC‑001, вернёт 404), потому что он логинит без пароля в т.ч. как SUPERADMIN.
  Демо идёт через обычный вход реальными демо‑аккаунтами: хеш пароля, rate‑limit,
  CSRF. Это безопасно и одинаково работает в dev и в проде.
- В локальной разработке (`DEBUG=1`) `/demo-login` ещё доступен. Флаг —
  `ALLOW_DEMO_LOGIN` (в проде `0`).

## Консоль модератора (обратная связь агенту)
- Зайти под `admin@demo.lv` → **Konsole** (`/admin/inbox`).
- Пишете указание на доработку → «Отправить». Ответ агента появляется в треде
  **сам, без перезагрузки** (авто-обновление).

**Как приходит ответ (важно, чтобы не ждать зря):**
1. **Живой ответ** пишет активная сессия агента (через agent-API
   `POST /agent/api/threads/{id}/reply`, ключ в `data/agent_api_key.txt`).
   То есть ответ приходит, пока агент реально работает над проектом.
2. **Всегда-активный захват 24/7** — воркфлоу `inbox-to-issues` (GitHub Actions,
   по расписанию): каждое сообщение модератора, ждущее ответа, превращается в
   **GitHub Issue** (её можно отдать Copilot coding agent на автономный PR).
   Так сообщение не теряется, даже если сейчас нет активной сессии.
   ⚠️ GitHub троттлит бесплатные cron — захват может запуститься не сразу
   (можно дёрнуть вручную: Actions → inbox-to-issues → Run workflow).
3. Проверить состояние из терминала:
   `KEY=$(cat data/agent_api_key.txt); curl -s -H "X-Agent-Key: $KEY" \
   https://skaititaji.onrender.com/agent/api/threads` — у отвеченных тредов
   `last_author=agent`, у ждущих — `last_author=moderator`.

**Почему бывает «агент не отвечает»:** живой ответ требует активной сессии
агента. Автоматический захват в Issue работает всегда, но это не мгновенный
чат-ответ. Быстрая проверка «на связи ли кто-то» — написать в тред: если рядом
активна сессия, ответ придёт; если нет — сообщение уйдёт в Issue и будет
обработано, когда сессия поднимется.

- Автономный агент-форк (ветка `agent/console`) при запуске слушает консоль и
  работает сам; мердж в `main` — по расписанию с гейтами (тесты/линт/безопасность).
- НЕ путать: локальный `tools/feedback_watch.py` — мост для **локальной** БД
  (dev). Он НЕ видит прод-консоль; для прода используется agent-API + issues.

## Контроль деплоя
- Хостинг: Render (autoDeploy с `main`). Прод не падает при неудачном деплое —
  Render держит старую версию, пока новая не пройдёт health‑check.
- Env для безопасности выставлены: `SECRETS_ENCRYPTION_KEY`, `ALLOW_DEMO_LOGIN=0`,
  `DEBUG=0`, `SECRET_KEY` (не дефолтный), `DATABASE_URL` (Postgres), `VISMA_MOCK=1`.
- Boot‑guard (`validate_production_config`) не даст стартовать проду с небезопасным
  конфигом.
