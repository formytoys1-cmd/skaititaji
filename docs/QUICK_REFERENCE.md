## Как работает демо (важно)
- На `/demo` и лендинге кнопки «Войти в демо» ведут на **`/login?demo=<role>`**
  (`resident`/`manager`/`admin`). Открывается форма входа с **уже заполненными**
  e‑mail и паролем — остаётся нажать зелёную кнопку «Войти».
- **Почему не «в один клик»:** в проде вход‑обход `/demo-login` **отключён**
  (SEC‑001, вернёт 404), потому что он логинит без пароля в т.ч. как SUPERADMIN.
  Демо идёт через обычный вход реальными демо‑аккаунтами: хеш пароля, rate‑limit,
  CSRF. Это безопасно и одинаково работает в dev и в проде.
- В локальной разработке (`DEBUG=1`) `/demo-login` ещё доступен. Флаг —
  `ALLOW_DEMO_LOGIN` (в проде `0`).

## Регистрация реальных пользователей (онбординг)
- **Житель** регистрируется на `/registreties`: имя, e‑mail, пароль и **номер
  лицевого счёта** квартиры (его выдаёт apsaimniekotājs). Аккаунт привязывается к
  квартире по account_number.
- **Подтверждение e‑mail:** после регистрации на почту уходит письмо со ссылкой
  `/verificet?token=…` (действует 24 ч). До подтверждения вход заблокирован
  (ведёт на повторную отправку `/verificet/atkartot`). Демо/eIDAS‑аккаунты уже
  verified.
  - Почта: SMTP через env `EMAIL_HOST/PORT/USER/PASSWORD/FROM` (free‑вариант —
    Gmail SMTP c app‑password). Если SMTP не настроен — письма пишутся в
    `data/outbox/` (для демо), без внешних сервисов.
- **Защита от ботов (free, без сервисов):** honeypot‑поле + подписанная HMAC
  метка времени (форма, отправленная за < 2 c или с поддельной меткой — бот) +
  существующие rate‑limit и CSRF. Само подтверждение e‑mail — главный барьер.
- **Вместимость квартиры ×2:** на одну квартиру можно зарегистрировать не больше
  `Unit.max_residents` жильцов (по умолчанию **2** — чтобы 2 человека могли
  подавать показания). Свыше — отказ с просьбой обратиться к управляющему.
- **Массовое заведение квартир (управляющий):** на странице дома
  `/parvalde/objekti/{id}` форма «Ģenerēt dzīvokļus»: подъезды × этажи × кв/этаж.
  Пример 119‑й серии (Islices 3): 2 подъезда × 10 этажей × 4 = **80 квартир** со
  сквозной нумерацией; каждой присваивается лицевой счёт и вместимость. Уже
  существующие номера пропускаются; лимит 2000 за раз.

## Консоль модератора (обратная связь агенту)
- Зайти под `admin@demo.lv` → **Konsole** (`/admin/inbox`).
- Пишете указание на доработку → «Отправить». Ответ агента появляется в треде
  **сам, без перезагрузки** (авто-обновление).

**Как приходит ответ (важно, чтобы не ждать зря):**
1. **Живой ответ** пишет активная сессия агента (через agent-API
   `POST /agent/api/threads/{id}/reply`, ключ в `data/agent_api_key.txt`).
   То есть ответ приходит, пока агент реально работает над проектом.
2. **Всегда-активный захват 24/7** — воркфлоу `inbox-to-issues` (GitHub Actions,
   по расписанию): каждое сообщение модератора, ждущее ответа, превращается в
   **GitHub Issue** (её можно отдать Copilot coding agent на автономный PR).
   Так сообщение не теряется, даже если сейчас нет активной сессии.
   ⚠️ GitHub троттлит бесплатные cron — захват может запуститься не сразу
   (можно дёрнуть вручную: Actions → inbox-to-issues → Run workflow).
3. Проверить состояние из терминала:
   `KEY=$(cat data/agent_api_key.txt); curl -s -H "X-Agent-Key: $KEY" \
   https://skaititaji.onrender.com/agent/api/threads` — у отвеченных тредов
   `last_author=agent`, у ждущих — `last_author=moderator`.

**Почему бывает «агент не отвечает»:** живой ответ требует активной сессии
агента. Автоматический захват в Issue работает всегда, но это не мгновенный
чат-ответ. Быстрая проверка «на связи ли кто-то» — написать в тред: если рядом
активна сессия, ответ придёт; если нет — сообщение уйдёт в Issue и будет
обработано, когда сессия поднимется.

- Автономный агент-форк (ветка `agent/console`) при запуске слушает консоль и
  работает сам; мердж в `main` — по расписанию с гейтами (тесты/линт/безопасность).
- НЕ путать: локальный `tools/feedback_watch.py` — мост для **локальной** БД
  (dev). Он НЕ видит прод-консоль; для прода используется agent-API + issues.

## Автономность 24/7 — что работает без сессии, а что нет
**Крутится 24/7 на GitHub Actions (сессия НЕ нужна):**
- `keepalive` (10 мин) — сайт не засыпает;
- `inbox-to-issues` (15 мин) — сообщения из консоли → GitHub Issue (не теряются);
- `console-control` (10 мин) — команда `[merge]` из консоли → запуск авто-мерджа;
- `reference-monitor` (30 мин) — жив ли сайт/QR/демо;
- `automerge` (6 ч) — слияние ветки форк-агента в `main` с гейтами;
- `standards-watch` / `quality-gates` (еженедельно).

**НЕ работает 24/7:** «живой» LLM-агент, который сам читает сообщение, думает,
правит код и отвечает текстом — это требует **активной сессии** (как эта).
Cron-скелет постоянный, но это фиксированные задачи, а не рассуждающий чат.

> **Решение проекта: работаем только на FREE.** Платные планы пока не
> рассматриваем. Всё текущее работает бесплатно (см. «Free-tier статус» ниже).
> Путь к 24/7 «живому» агенту (Copilot coding agent) требует платного плана
> Copilot — **ПРИПАРКОВАН**. Инструкция на будущее: `docs/COPILOT_CODING_AGENT_SETUP.md`.
> Код авто-назначения в `inbox_to_issues.py` безопасно бездействует, пока фича
> не включена, — включится сам, если когда-нибудь перейдём на платный план.

## Free-tier статус (всё бесплатно)
- **GitHub Actions** — репо **публичный** ⇒ минуты **безлимитны и бесплатны**.
  Весь cron-скелет (keepalive, inbox-to-issues, мониторы, automerge) — free.
- **Render Web** — free-инстанс (засыпает; `keepalive` будит каждые 10 мин).
- **Render Postgres** — free-план. ⚠️ **ВАЖНО: free-БД истекает `2026-09-18`**
  (создана 2026-08-19). После этой даты Render удаляет бесплатную БД —
  **риск потери данных**. Напоминание: воркфлоу `db-expiry-watch` (ежедневно)
  заведёт GitHub Issue за 14 дней до истечения.
  - Бесплатные варианты без срока: **Neon** (neon.tech), **Supabase**
    (supabase.com). План: создать free-БД → сменить `DATABASE_URL` на Render →
    `alembic upgrade head` применится сам (миграции самовосстанавливающиеся).
- **Секреты** — не в репо (gitignored: `data/agent_api_key.txt`,
  `_secrets_encryption_key.txt`, `_pg_ext.txt`); токенов в коде нет (важно для
  публичного репо).

## Контроль деплоя
- Хостинг: Render (autoDeploy с `main`). Прод не падает при неудачном деплое —
  Render держит старую версию, пока новая не пройдёт health‑check.
- Env для безопасности выставлены: `SECRETS_ENCRYPTION_KEY`, `ALLOW_DEMO_LOGIN=0`,
  `DEBUG=0`, `SECRET_KEY` (не дефолтный), `DATABASE_URL` (Postgres), `VISMA_MOCK=1`.
- Boot‑guard (`validate_production_config`) не даст стартовать проду с небезопасным
  конфигом.
