# Отчёт: Лучшие практики веб-дизайна (MailerLite) и их применимость к Skaitītāji

---

## ЧАСТЬ 1. Полный перечень практик из статьи MailerLite

Статья описывает **14 практик**. Ниже — каждая с раскрытием «что / почему / как внедрить».

---

### 1. Начинайте с шаблона

**Что:** Использовать готовый, профессионально спроектированный шаблон как отправную точку.

**Почему:** Экономит время, встраивает проверенные практики иерархии и spacing с нуля, снижает ошибки «дизайна с чистого листа».

**Как:** Выбрать шаблон, соответствующий категории (SaaS, утилита), заменить контент и цвета под бренд, не ломая структуру. Определить глобальные стили (цвета, шрифты, отступы) в системе дизайна ещё до начала верстки.

---

### 2. Единообразие дизайна на всём сайте

**Что:** Одни и те же шрифты, цвета, логотип, скругления, тени, паттерны кнопок — на каждой странице.

**Почему:** Формирует узнаваемость бренда, снижает когнитивную нагрузку — пользователь не заново учится читать интерфейс на каждой странице. Экономит время разработки.

**Как:**
- Определить палитру из 3–5 цветов (основной/акцентный/нейтральный/текст/фон).
- Использовать цветовую психологию: синий/зелёный → доверие, надёжность; красный → срочность/ошибки; серый → нейтральность.
- Ограничиться 2–3 шрифтами (заголовок + тело + опционально моноширинный).
- Зафиксировать глобальные стили в CSS-переменных/Tailwind-конфиге **до** начала вёрстки.
- Тот же стиль переносить на email, соцсети, печатные материалы.

---

### 3. Визуальная иерархия

**Что:** Упорядочить элементы страницы так, чтобы взгляд автоматически двигался от самого важного к деталям.

**Почему:** Посетитель принимает решение остаться или уйти за 5–15 секунд. Без иерархии глаз «блуждает» и ключевое сообщение теряется.

**Как:**
- Самое важное — самый крупный шрифт, вверху, на первом экране.
- Используйте размер, цвет, контрастность и отступы для управления вниманием.
- CTA выделяется контрастным цветом по отношению к фону.
- Второстепенные элементы — мельче, ниже.
- Применяйте паттерны F-reading (для контентных страниц с большим текстом) и Z-pattern (для лендингов/страниц с минимумом текста): в Z-паттерне важнейшее — в верхнем левом углу, затем по диагонали.

---

### 4. Пространство (whitespace / negative space)

**Что:** Осознанные пустые зоны между элементами страницы.

**Почему:** Без отступов контент «слипается», читаемость резко падает. Whitespace визуально группирует связанные элементы (принцип близости), даёт «воздух» и направляет взгляд.

**Как:**
- Добавлять вертикальные отступы между секциями (padding/margin).
- Связанные элементы располагать ближе друг к другу, несвязанные — дальше (группировка без линий/рамок).
- Контролировать line-height и letter-spacing в тексте.
- Не бояться «пустоты» — она не потеря места, а инструмент.

---

### 5. Навигация — простота и доступность

**Что:** Структура меню, хлебные крошки, строка поиска, ссылки в тексте, аккордеоны для FAQ.

**Почему:** Пользователь должен находить любую важную страницу максимум за 3 клика. Путаная навигация = уход.

**Как:**
- Header: логотип (→ главная), меню с приоритетными разделами, кнопка входа с контрастным цветом, кнопка выхода для авторизованных.
- Breadcrumbs — если сайт многоуровневый.
- Поиск — если страниц много.
- Аккордеоны для FAQ — чтобы не перегружать страницу текстом.
- Принцип «3 клика» — любая важная страница доступна не более чем за 3 клика.

---

### 6. Sticky-навигация

**Что:** Шапка «прилипает» к верху при скролле.

**Почему:** Пользователь в любой точке страницы имеет доступ к меню и CTA, не нужно скроллить обратно наверх.

**Как:** `position: sticky; top: 0` в CSS. На мобильных — компактная (hamburger icon). Должна быть максимально ненавязчивой — минимальная высота, без анимации при появлении.

---

### 7. Доступность (Accessibility / WCAG)

**Что:** Веб-сайт должен работать для людей с ограниченными возможностями.

**Почему:** Юридические требования (в EU — EAA, в Латвии — обязательно для публичных сервисов), охват более широкой аудитории, влияние на SEO.

**Как (ключевые рекомендации WCAG):**
- Alt-текст для всех нетекстовых элементов (изображения, кнопки-иконки).
- Транскрипты/субтитры для аудио/видео.
- Достаточный цветовой контраст (минимум 4.5:1 для обычного текста, 3:1 для крупного).
- Управление с клавиатуры (Tab, Enter, Escape) — видимый focus-outline.
- Нет контента, провоцирующего эпилептические приступы (> 3 вспышек/сек).
- Структурированные заголовки (h1 → h2 → h3) для скринридеров.
- ARIA-атрибуты там, где семантики HTML не хватает.
- Skip-link «перейти к содержанию» в начале страницы.

---

### 8. CTA — призыв к действию

**Что:** Каждая страница имеет одну главную цель, и CTA подталкивает к ней.

**Почему:** Без явного CTA пользователь не знает, что делать, и уходит. Контрастная кнопка привлекает взгляд автоматически.

**Как:**
- Размещать CTA на видном месте (первый экран + повтор ниже).
- Цвет кнопки — контрастный к фону страницы.
- Текст CTA — конкретный, ориентированный на действие («Подать показания», «Войти в кабинет», а не «OK» или «Далее»).
- Несколько кнопок на длинной странице (вверху + внизу).
- Sticky CTA в шапке остаётся при скролле.
- Разные CTA для разных страниц (лендинг vs. страница помощи).

---

### 9. Адаптивный (responsive) дизайн

**Что:** Сайт одинаково хорошо выглядит на любом устройстве и размере экрана.

**Почему:** >50% трафика — мобильный. Google использует mobile-first индексацию (с 2019 г.). Нечитабельный мобильный — это потеря и пользователей, и позиций в поиске.

**Как:**
- CSS breakpoints: минимум mobile (<640px), tablet (640–1024px), desktop (>1024px).
- Вертикальный stack на мобильном вместо горизонтального grid.
- Шапка сворачивается в hamburger.
- Touch targets — минимум 44×44px (Apple HIG) / 48×48dp (Google Material) для кнопок.
- Проверять: `<meta name="viewport" content="width=device-width, initial-scale=1">`.

---

### 10. Уникальность и отличимость бренда

**Что:** Визуальная и текстовая идентичность, которую не спутаешь с другими.

**Почему:** В конкурентной среде безликий сайт не запоминается. Уникальность строит доверие и приверженность.

**Как:**
- Фотографии реальной команды (не стоковые).
- Уникальный персонаж/маскот (опционально).
- Фирменные цвета, нетипичные для ниши.
- Сильный текст «About» с ценностями компании.
- Анимации при скролле (осторожно — с учётом `prefers-reduced-motion`).

---

### 11. Соблюдение устоявшихся паттернов UX (конвенции)

**Что:** Использовать то, что пользователи уже знают: лого → домой, подчёркивание/цвет = ссылка, шестерёнка = настройки, hamburger = меню, иконки соцсетей.

**Почему:** Пользователь мгновенно понимает интерфейс без обучения. Нарушение конвенций создаёт трение и раздражение.

**Как:**
- Логотип в левом верхнем углу, кликабельный.
- Ссылки — визуально отличимы (цвет, подчёркивание).
- Единая иконография (не смешивать стили иконок).
- Стандартные иконки для соцсетей, магазинов приложений.
- Кнопки — выглядят как кнопки (рельеф, граница или заливка).

---

### 12. SEO-оптимизация дизайна

**Что:** Технические и визуальные решения, влияющие на ранжирование.

**Почему:** Google — источник бесплатного целевого трафика. Дизайн напрямую влияет на Core Web Vitals.

**Как:**
- **Скорость загрузки:** WebP/AVIF вместо JPG/PNG; избегать слайдеров и тяжёлых элементов above-the-fold; lazy loading для изображений; минификация CSS/JS.
- **Core Web Vitals:** LCP (largest contentful paint) < 2.5с; CLS (cumulative layout shift) → 0; INP < 200мс.
- **Изображения:** описательные имена файлов, alt-теги.
- **Семантический HTML:** правильные h1/h2/h3, title, meta description.
- **Mobile-first:** адаптивность = фактор ранжирования.
- Ключевые слова в заголовках и тексте страниц.

---

### 13. Формы регистрации/обратной связи

**Что:** Юзабельные, минималистичные формы, соответствующие общему стилю сайта.

**Почему:** Формы — точка конверсии. Плохая форма = брошенный процесс.

**Как:**
- Заголовок формы — главная польза («Подать показания за январь»).
- Описание — уточняет детали.
- Подпись к каждому полю над полем (не placeholder вместо label).
- CTA кнопка — конкретная («Отправить показания», не просто «Отправить»).
- Pop-up'ы: всегда заметная кнопка закрытия; не перекрывать ключевые элементы; показывать после задержки; ясное объяснение, на что подписываешься.
- Inline-валидация с понятными сообщениями об ошибках.

---

### 14. Аналитика и A/B-тестирование

**Что:** Непрерывное измерение и улучшение дизайна на основе данных.

**Почему:** Запуск сайта — не финал. Реальное поведение пользователей часто расходится с предположениями дизайнеров. Даже +1% конверсии = значимый результат.

**Как:**
- Подключить Google Analytics или аналог (Plausible, Umami для GDPR-friendly).
- Отслеживать: популярные страницы, источники трафика, клики, время на странице, путь по воронке.
- A/B-тесты: менять **один** элемент (цвет кнопки, текст CTA, расположение формы), запускать обе версии параллельно, ждать статистической значимости, итерировать.

## ЧАСТЬ 3. Приоритизированный список конкретных улучшений UI/UX

Фокус: ясность, доверие, читабельность, конверсия **лендинга + первого запуска жильца**.

---

### 🔴 КРИТИЧНО (делать в первую очередь)

---

**1. Устранить CDN Tailwind в production — заменить на compiled/purged CSS**

**Проблема:** `<script src="https://cdn.tailwindcss.com">` — рендер-блокирующий скрипт (~350KB), обрабатывает весь Tailwind в браузере. FCP/LCP деградирует, особенно на мобильных в Латвии на 4G.

**Как:** Добавить `tailwindcss` в build pipeline (PostCSS + `@tailwindcss/cli` или Vite), генерировать `static/css/app.css` с только используемыми классами (~5–15KB). В `base.html` заменить script-тег на `<link rel="stylesheet" href="/static/css/app.css">`.

**Почему критично:** Это одновременно Core Web Vitals (SEO), UX и надёжность (CDN fallback).

---

**2. Добавить labels к полям ввода показаний счётчиков**

**Проблема:** В `dashboard.html` строка каждого счётчика содержит `<input name="value_{{ m.meter.id }}" ...>` без явного `<label for="...">`. Скринридер не может идентифицировать поле. Нарушение WCAG 1.3.1 (Info and Relationships) и 4.1.2 (Name, Role, Value).

**Как:**
```html
<label for="val_{{ m.meter.id }}" class="sr-only">
  {{ meter_name(m.type) }} Nr. {{ m.meter.serial_number }} ({{ t('res.reading') }}, {{ m.type.unit }})
</label>
<input id="val_{{ m.meter.id }}" name="value_{{ m.meter.id }}" ...>
```
Добавить `id=` к `<input>` и `<label for="...">` (можно `sr-only` для визуально чистого дизайна).

**Почему критично:** WCAG 2.2 AA — обязательное требование, явно заявленное в продукте.

---

**3. Исправить touch targets до минимума 44×44px**

**Проблема:** `base.html` line 28: `a, button { min-height: 24px }` — вдвое меньше стандарта Apple HIG и WCAG 2.5.8 (Target Size Minimum, 24×24px CSS — это новое требование 2.2, но лучшая практика — 44×44px).

**Как:** Изменить:
```css
a, button, input[type="submit"], select { min-height: 44px; }
```
Или прицельно применить padding: `py-3 px-4` к интерактивным элементам в шапке (lang switcher, nav links).

**Почему критично:** Жильцы часто заходят с мобильного. Мелкие ссылки LV/RU/EN в шапке сейчас практически не нажимаемы пальцем.
