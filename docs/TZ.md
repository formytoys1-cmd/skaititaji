# Техническое задание (ТЗ)
## Платформа подачи показаний счётчиков «Skaitītāji»

**Версия:** 1.0 · **Дата:** 2026-08 · **Статус:** рабочее ТЗ для MVP + демо

Документ основан на исследовании латвийского рынка, законодательства и API Visma
Horizon. Первоисточники:
- [Водоводы и законодательство ЛР](research_water_suppliers.md)

## 1. Цель и видение

Создать удобную, надёжную и **легко масштабируемую** SaaS‑платформу для подачи
показаний счётчиков. Приоритет №1 — вода (холодная/горячая), но архитектура
**config‑driven**: новые типы счётчиков (электричество, газ, тепло) добавляются как
данные, без изменения кода.

Платформа **мультиарендная (multi‑tenant)**: любая организация (управляющий домами
`apsaimniekotājs`, жилищный кооператив `DzĪKS`, водоснабжающее предприятие
`ūdenssaimniecība`) получает изолированное пространство с собственным брендингом,
настройками окна подачи и интеграцией с учётной системой.

## 2. Доменный контекст (из исследования)

### 2.1 Двухуровневая модель учёта воды в Латвии

- **Уровень 1 — Водовод ↔ Дом.** Согласно `Ūdenssaimniecības pakalpojumu likums`
  §8(2), потребителем услуги для многоквартирного дома является **управляющий**
  (не отдельный житель). На вводе в дом стоит коммерческий прибор учёта
  **KUM** (`komercuzskaites mēraparāts`). Водовод выставляет счёт управляющему за
  весь дом.
- **Уровень 2 — Управляющий ↔ Жильцы.** Квартирные счётчики (ХВС/ГВС) —
  внутридомовые, юридически **не** коммерческие. Жильцы подают показания
  **управляющему**. Управляющий суммирует квартирные счётчики, сверяет с KUM и
  распределяет разницу `starpība` между квартирами (по потреблению или площади).

> **Вывод для продукта:** основной арендатор платформы — **управляющий**. Житель
> подаёт показания в пространство своей организации. Платформа также поддерживает
> сценарий, где арендатор — сам водовод (прямой сбор показаний).

### 2.2 Ключевые нормы (MK noteikumi Nr. 174, likumi.lv/ta/id/281230)

- **§41:** если показания не поданы в срок — расход считается по **среднему за
  предыдущие 12 месяцев**.
- **§42:** такой расчётный режим — не дольше **3 месяцев** (1 месяц при снятом/
  неисправном приборе), затем перерасчёт.
- **§39:** при отсутствии счётчика — по нормам потребления самоуправления × число
  зарегистрированных лиц.
- **§35:** допускается телеметрия (дистанционное снятие).

### 2.3 Окна подачи (различаются по организациям)

| Организация | Окно подачи |
|---|---|
| Rīgas ūdens | 20 — последний день месяца |
| Rēzeknes ūdens | 28 — 3 число след. месяца |
| Типовой управляющий | 25 — 5 число след. месяца |

→ Окно подачи — **настройка организации** (`reading_day_from`, `reading_day_to`),
с поддержкой перехода через границу месяца.

### 2.4 Обязательные поля формы подачи (эталон — Rēzeknes ūdens)

Адрес, Имя/Фамилия, Клиентский номер (`klienta numurs`), Серийный № счётчика,
Показание (м³), Дата, Телефон/Email, Фото счётчика (серийный номер должен быть
виден), Подпись (на бумаге). Для ГВС — отдельные № и показание.

### 2.5 Специфика горячей воды

ГВС измеряется в м³, но при централизованном теплоснабжении в счёт добавляется
**тепловая энергия** на нагрев (МВт·ч). Поэтому тип счётчика должен нести единицу
измерения и десятичную точность как данные (config‑driven), а не хардкодиться.

## 3. Роли пользователей

| Роль | Возможности |
|---|---|
| **Житель** (`resident`) | Видит свои квартиры и счётчики, подаёт/корректирует показания, видит историю и расход. |
| **Управляющий** (`manager`) | Панель по дому: прогресс подачи, аномалии, приём/отклонение, выгрузка в учётную систему. |
| **Суперадмин** (`superadmin`) | Организации (аренды), каталог типов счётчиков, статус интеграций, открытый API. |

Планово (из анализа конкурентов): вход через **Smart‑ID / eParaksts / банк**
(eIDAS) — ни один активный конкурент этого не даёт → конкурентное преимущество.

## 4. Функциональные требования

### 4.1 Подача показаний (ядро)
- FR‑1. Карточка каждого счётчика: тип, иконка, № прибора, местоположение,
  **предыдущее показание** и дата.
- FR‑2. Ввод нового показания с **live‑расчётом расхода** и валидацией:
  - показание ≥ предыдущего (счётчик не «откручивается»);
  - расход ≤ порога правдоподобия типа → иначе пометка **аномалия**;
  - повторная подача за период заменяет предыдущую.
- FR‑3. Индикатор **окна подачи** (открыто/закрыто), но приём вне окна не блокируется.
- FR‑4. Пакетная подача всех счётчиков квартиры одной формой.
- FR‑5. (Roadmap) Загрузка **фото счётчика** + OCR‑распознавание цифр.

### 4.2 Кабинет управляющего
- FR‑6. Дашборд: сдано/не сдано, % прогресса, число аномалий, не синхронизировано.
- FR‑7. Таблица статуса по всем счётчикам периода с подсветкой аномалий.
- FR‑8. Выгрузка показаний в учётную систему (Visma Horizon) одним действием.
- FR‑9. Журнал интеграции (аудит выгрузок).
- FR‑10. (Roadmap) Расчёт `starpība` KUM vs сумма квартирных, распределение.
- FR‑11. (Roadmap) §41‑оценка (среднее за 12 мес.) для несдавших.

### 4.3 Администрирование платформы
- FR‑12. Список организаций (аренды) + статус интеграции.
- FR‑13. Каталог типов счётчиков: просмотр, включение/выключение, **добавление
  нового типа без кода**.
- FR‑14. Открытый JSON API: `/api/health`, `/api/meter-types`, `/api/organizations`.

### 4.4 Мультиарендность
- FR‑15. Данные организаций изолированы; у организации — свой бренд‑цвет, логотип,
  окно подачи, провайдер интеграции и его конфиг.
- FR‑16. Новую организацию можно завести, передав её данные (реквизиты, дома,
  квартиры, счётчики) — платформа сразу готова к подаче.

## 5. Нефункциональные требования

- **Масштабируемость:** stateless‑веб‑слой, отделённый слой интеграций
  (провайдеры подключаются реестром), БД заменяема (SQLite→PostgreSQL сменой
  `DATABASE_URL`).
- **Расширяемость:** тип счётчика и доп. поля формы — данные (`MeterType`,
  JSON‑`field_schema`), а не код.
- **Безопасность:** хэширование паролей (PBKDF2), сессии в подписанной cookie;
  секреты — из окружения; готовность к eIDAS‑входу.
- **Наблюдаемость:** журнал интеграций (`IntegrationLog`).
- **Локализация:** UI на латышском; типы счётчиков хранят LV/RU/EN названия;
  архитектура готова к полной мультиязычности (важно RU для Латвии).
- **Демо‑режим:** интеграция Visma работает в mock‑режиме без реального сервера.

## 6. Модель данных

```
Organization (арендатор: управляющий / кооператив / водовод)
  ├─ brand, reading window, integration_provider + integration_config(JSON)
  ├─ Building (дом; external_id ↔ объект в учётной системе)
  │    └─ Unit (квартира; account_number = klienta numurs)
  │         └─ Meter (счётчик; serial_number, meter_type, external_id, поверка)
  │              └─ Reading (period YYYY-MM, value, consumption, source, status, anomaly)
  └─ User (resident / manager / superadmin)
       └─ UnitResident (связь житель ↔ квартира, owner/tenant)

MeterType (ГЛОБАЛЬНЫЙ config-driven каталог)
  code, category, name_lv/ru/en, unit, decimals, icon, color,
  max_plausible_consumption, allow_zero, field_schema(JSON)

IntegrationLog (аудит синхронизаций)
```

Статусы показания: `submitted → accepted → synced` (или `rejected`).
Источники: `web | manager | import | estimated(§41) | operator(телеметрия)`.

## 7. Интеграция с Visma Horizon REST API

Детали — в [research_visma_horizon.md](research_visma_horizon.md). Существенное:

- **Хостинг on‑premise**, базовый URL индивидуален: `https://<server>/API/rest/`.
- **Auth:** HTTP Basic (пользователь Horizon с правами модулей **NĪP** и **KNS**).
- **Формат:** JSON; списочные сервисы (SL) — `/query` (filter/columns/orderby/limit)
  и инкрементальная синхронизация `/sync/new`, `/sync/changed`.
- **Сервисы:**
  - Счётчики: `TdmPNSSkaBL` (NĪP), `TdmKNSkaBL` (KNS);
  - Чтение показаний: `TdmPNSSkaLigRadSL`, `TdmPNSSkaNolRadSL` (SL);
  - **Запись показаний:** через акт `TdmPNSPnaSkaIzmBL` (BL, по шаблону), т.к. SL —
    только чтение;
  - Клиенты `TdmPNSKlientsBL`, договоры `TdmPNSWEBClientContractsSL`,
    квартиры `TdmPNSTGBL`, счета `TdmPNSRekBL`;
  - Health: `GET /API/rest/global/healthCheck`.

Абстракция `AccountingIntegration` изолирует провайдера; `VismaHorizonClient`
реализует интерфейс и имеет **mock‑режим** для демо. Другие ERP (Namejs, ZZ
Dats/Dativa, WinNAMS) подключаются добавлением реализации в реестр.

## 8. Архитектура и стек демо

- **Backend:** Python 3, FastAPI, SQLModel (SQLAlchemy), Jinja2.
- **Frontend:** серверный рендеринг + Tailwind (CDN), минимальный JS
  (live‑расчёт расхода) — без сборочного пайплайна, мгновенный запуск.
- **БД:** SQLite (демо) → PostgreSQL (прод) сменой `DATABASE_URL`.
- **Слои:** `models` (данные) · `services` (бизнес‑логика подачи) ·
  `integrations` (провайдеры ERP) · `routers` (public/auth/resident/manager/admin)
  · `templates` (UI).

## 9. Дорожная карта

**MVP (реализовано в демо):** мультиарендность, config‑driven типы счётчиков,

админа, выгрузка в Visma Horizon (mock), открытый API, демо‑данные.

**Фаза 2:** eIDAS‑вход (Smart‑ID/eParaksts/банк), фото+OCR показаний, §41‑оценка,
расчёт `starpība`, e‑mail/SMS‑напоминания, графики потребления, полная RU/LV/EN.

**Фаза 3:** мобильное приложение (Face/Touch ID, push), реальный коннектор Visma
Horizon (по XSD сервисов на конкретной инсталляции), онлайн‑оплата, модуль
«Mājas lieta», биллинг арендаторов платформы.

## 10. Критерии приёмки демо

1. Публичный лендинг + страница демо‑доступа открываются.
2. Житель входит и подаёт показания ХВС/ГВС; расход считается; аномалии
   помечаются; повторная подача заменяет.
3. Управляющий видит прогресс/аномалии и **выгружает показания в Visma Horizon**
   (mock), запись фиксируется в журнале.
4. Админ добавляет **новый тип счётчика без изменения кода** и видит его в системе.
5. Открытый API отдаёт типы счётчиков и организации.
