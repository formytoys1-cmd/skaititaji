# Деплой платформы «Skaitītāji» на бесплатный хостинг

Приложение готово к контейнерному и PaaS-деплою: слушает `$PORT`, база
переключается на PostgreSQL через `DATABASE_URL`, секреты — из окружения.
В демо‑режиме используется SQLite и mock‑интеграция Visma (данные сеются при
старте).

Ниже — три бесплатных варианта. Рекомендация зависит от того, готовы ли вы
привязать биллинг‑аккаунт (нужен только для Google Cloud, даже на бесплатном
ярусе).

---

## Вариант A — Google Cloud Run (нативно «через Google‑аккаунт»)

Бесплатный ярус Cloud Run щедрый, но проект должен иметь привязанный billing
account (карта; списаний в пределах бесплатного яруса не будет).

Разовая настройка:
```bash
brew install --cask google-cloud-sdk      # если gcloud не установлен
gcloud auth login                          # вход вашим Google-аккаунтом (браузер)
gcloud projects create skaititaji-demo --name="Skaititaji"   # или существующий
# привязать billing account в консоли: https://console.cloud.google.com/billing
```

Деплой одной командой:
```bash
PROJECT_ID=skaititaji-demo ./tools/deploy_cloudrun.sh
```
Скрипт включит нужные API, соберёт контейнер (Cloud Build из `Dockerfile`) и
задеплоит публичный сервис, напечатав URL.

> Файловая система Cloud Run эфемерна — для демо это нормально (данные сеются
> заново при старте). Для постоянных данных подключите Cloud SQL (PostgreSQL) и
> задайте `DATABASE_URL`.

## Вариант B — Render.com (проще всего, без биллинга)

Render даёт бесплатный web‑сервис и авто‑деплой из Git. Регистрация возможна
через Google‑аккаунт.

1. Залейте репозиторий на GitHub (см. ниже).
2. На render.com → **New → Blueprint**, укажите репозиторий.
3. Render прочитает [`render.yaml`](render.yaml) и создаст сервис; каждый
   `git push` будет авто‑деплоить.

Бесплатный инстанс «засыпает» при простое — первый запрос будит его (несколько
секунд). Для демо приемлемо.

## Переменные окружения (прод)

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | секрет подписи сессий (обязательно задать) |
| `DATABASE_URL` | `postgresql://...` для постоянных данных (иначе SQLite) |
| `VISMA_MOCK` | `1` — демо без Horizon; `0` — реальный сервер |
| `VISMA_BASE_URL`, `VISMA_USERNAME`, `VISMA_PASSWORD` | доступ к Visma Horizon |
| `PORT` | порт (задаёт хостинг автоматически) |

## Что мне нужно от вас для автодеплоя

Чтобы я задеплоил автоматически, выберите вариант и предоставьте доступ:
- **Cloud Run:** ID GCP‑проекта с привязанным биллингом + разрешение на
  `gcloud auth login` (интерактивный вход) либо ключ сервис‑аккаунта (JSON).
- **Render/Railway/Fly:** доступ к GitHub‑репозиторию (или разрешение создать
  его) — дальше деплой настраивается по `render.yaml`/`Dockerfile`.

Интерактивный вход в Google и привязку биллинга я выполнить за вас не могу —
это требует ваших учётных данных.

## PostgreSQL (постоянные данные) — ПОДКЛЮЧЕНО

Боевой сайт использует управляемую **PostgreSQL** на Render (не эфемерный SQLite),
поэтому введённые данные (дома, квартиры, счётчики, регистрации, показания)
сохраняются между перезапусками.

- Драйвер: `psycopg[binary]` (psycopg 3). `app/database.py` нормализует
  `postgres://` → `postgresql+psycopg://` и включает `pool_pre_ping`.
- Переключение — только через переменную окружения `DATABASE_URL`. Локально по
  умолчанию SQLite (демо), в проде — Postgres.
- БД и web-сервис должны быть в **одном регионе** (у нас Oregon) — тогда
  работает internal connection string (быстро, без публичного трафика).
- `SECRET_KEY` и `DEBUG=0` заданы как переменные окружения сервиса.
- Схема создаётся автоматически (`SQLModel.metadata.create_all`), демо-данные —
  идемпотентным `seed_demo()` (демо-организация не дублируется).

Проверено: создан объект → выполнен рестарт сервиса → объект остался на месте.
